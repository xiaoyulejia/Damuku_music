# 多场景自动切换问题修复方案

## 本轮问题

当前手动切换已经正常，需要修复：

1. 勾选“自动切换”后，设置有时没有保存或很快恢复成未勾选；
2. 自动逻辑能够识别目标场景，但没有真正完成播放端切换；
3. 下拉列表长期显示“instance 冲突”，即使只配置了一个对应场景来源。

本方案只影响显式开启的直播姬多场景模式。普通 OBS 地址：

```text
http://127.0.0.1:8000/order/?roomid=房间号&source=obs
```

不登记 candidate、不参与自动 switch，现有 OBS 播放、歌词和租约逻辑保持不变。

## 设置结构

```json
{
  "display": {
    "multiSceneHandoffEnabled": false,
    "multiSceneAutoSwitchEnabled": false,
    "multiSceneHeartbeatThresholdMs": 5000
  }
}
```

- 总开关默认关闭；
- 自动切换默认关闭；
- 只有总开关开启时才能勾选自动切换；
- 心跳阈值只在两个开关同时开启时生效；
- 关闭自动切换不能中断当前 publisher；
- 关闭总开关不能让普通 OBS 页面进入 candidate 模式。

## 问题一：自动切换设置没有稳定保存

### 已确认的现状

checkbox、设置收集和 PUT 保存代码都已经存在：

- `index.html` 有 `multiSceneAutoSwitchEnabled`；
- `getDisplaySettings()` 会读取 checkbox；
- onchange 会调用 `publishDisplaySettings()`；
- `/live/settings` PUT 会保存 `display`；
- `local-store` 会合并自动开关和心跳阈值。

因此问题不是“遗漏 onchange”，而是设置请求竞态。

### 根因：旧 GET 覆盖新 PUT

页面每 5 秒自动 GET 一次权威设置，同时 checkbox 改变会发送 PUT。

可能出现：

```text
1. 定时 GET 开始，请求时服务端 auto=false
2. 用户勾选自动切换
3. PUT 保存 auto=true，并返回新 revision
4. 第 1 步的旧 GET 较晚返回
5. applyAuthoritativeSettings 无条件应用旧数据
6. checkbox 又被改回 false，revision 也被回退
```

下一次保存会携带旧 revision，可能继续触发 `409`，让用户感觉设置无法保存。

另一个风险是播放器自己的设置读取直接写入 `window.__displaySettings`，但没有 revision 保护，也可能覆盖主设置流程中的新值。

### 修复方案：统一版本保护

`applyAuthoritativeSettings()` 不能无条件应用响应。需要比较：

```text
incoming.globalRevision
incoming.roomRevision
incoming.revision
```

建议规则：

```js
if (incoming.globalRevision < currentGlobalRevision) return false;
if (incoming.roomRevision < currentRoomRevision) return false;
if (incoming.revision < currentRevision) return false;
```

只有不旧于当前状态的响应才能更新：

- `serverDisplaySettings`；
- `window.__displaySettings`；
- checkbox；
- settings revision；
- 播放器的多场景设置。

### 保存期间处理定时 GET

增加：

```text
settingsSaveInFlight
settingsRequestSequence
settingsSaveQueue
```

建议执行方式：

1. checkbox 改变后立即更新本地 UI；
2. 将 PUT 加入串行保存队列；
3. PUT 进行中暂停定时 GET，或 abort 已经开始的旧 GET；
4. PUT 成功后只应用 PUT 返回的权威设置；
5. 更新 revision 后恢复定时 GET；
6. 晚到的旧 GET 根据 revision/sequence 被丢弃；
7. PUT 失败时再主动拉取一次最新设置并提示保存失败。

多个 checkbox 快速变化可以使用 100～200ms debounce 合并为一次 PUT，但保存请求本身仍必须串行。

### 禁止播放器直接覆盖全局设置

`music-player.waitForManualHandoffSettings()` 不应直接执行无版本信息的：

```js
window.__displaySettings = { ...旧值, ...响应值 };
```

推荐：

- 页面只由一个 settings store 管理权威设置；
- music-player 通过带 revision 的事件接收；
- 或让 music-player 的 GET 也调用相同的版本保护函数；
- 不允许两个模块分别维护 revision 不一致的设置副本。

### UI 保存状态

设置页显示：

```text
正在保存...
已保存
保存冲突，已重新读取
保存失败，请重试
```

不能静默把 checkbox 改回去。

### 验收测试

1. 人为延迟旧 GET，让它在新 PUT 后返回，checkbox 仍保持 true；
2. 最终 GET `/live/settings` 返回 `multiSceneAutoSwitchEnabled=true`；
3. 连续切换总开关、自动开关和阈值不会产生 revision 回退；
4. PUT 期间的定时 GET 被暂停、取消或忽略；
5. music-player 的设置请求不能覆盖较新 revision；
6. 收到真实 409 时重新读取并明确提示用户；
7. 刷新页面后自动开关仍为已保存状态。

## 问题二：识别到目标但没有真正自动切换

### 根因一：自动判断依赖控制页轮询

当前自动评估只在：

```text
GET /live/sync-candidates
```

中执行。只有 `source=control` 页面每秒轮询该接口。

如果没有常驻控制页：

```text
scene-a/scene-b candidate 仍正常 heartbeat
→ 后端记录的心跳年龄可以判断目标
→ 但 evaluateAutoSwitch 没有被调用
→ requestSceneSwitch 不会执行
```

自动切换不应依赖用户额外打开一个控制页面。

### 根因二：目标接管缺少可靠重试

后端识别目标后会创建 `target-pending`。目标页面下一次 candidate heartbeat 收到：

```json
{
  "activationRequested": true,
  "switchId": "auto-..."
}
```

然后调用 `tryReclaimPublisher(switchId)`。

但当前 handoff 页面：

- 必须可见；
- 必须携带 switchId；
- 普通 publisher retry 在 handoff 模式中被禁用；
- visibility 恢复路径调用的是无参数 `tryReclaimPublisher()`；
- 如果携带 switchId 的那次 heartbeat 丢失，没有持续重试。

因此页面可以停在 `target-pending`，控制页看起来已经识别目标，但 publisher 没有完成 claim。

### 根因三：自动完成状态没有写回

目标 claim 成功会把 handoff 标记为 `completed`，但自动状态没有对应写入：

```text
autoSwitch.state = completed
```

下一轮 evaluator 可能直接回到 `waiting/current-publisher-active`。因此即使实际切换成功，UI 也可能始终不显示“自动切换完成”。

### 根因四：已经选中的目标仍被本地 visibility 拦截

自动和手动后端都能生成 `target-pending + switchId`，但目标页面的 `tryReclaimPublisher(switchId)` 仍包含：

```text
handoffVisible 必须为 true
switchId 必须非空
```

直播姬不保证可靠更新标准页面可见性。于是会出现：

```text
后端已经识别 scene-b
→ autoSwitch.targetInstanceId = scene-b
→ handoff 可能已经 target-pending
→ scene-b heartbeat 收到 switchId
→ handoffVisible 仍为 false
→ tryReclaimPublisher 直接 return
→ 没有发送有效 sync-claim
```

表现正是“自动选择正确，但效果像没有点击切换”。

手动点击有时正常，是因为用户先切到目标场景、等待页面稳定后再点击，目标页面较可能已经把本地 visible 标志更新为 true。自动模式更早触发，更容易撞到这个竞态。

后端签发且与 `instanceId + activationId` 匹配的 switchId 已经是权威接管许可。目标页面不应再依赖不可靠的本地 visibility 决定是否 claim。

### 修复方案一：在 candidate heartbeat 中触发自动判断

candidate heartbeat 是自动模式下必然存在的事件。每次 `POST /live/sync-candidate` 完成候选更新后，在同一个房间锁中执行：

```text
更新 candidate
→ 清理过期 activation
→ evaluateAutoSwitch
→ 如果 shouldSwitch，调用 requestSceneSwitchLocked
→ 返回 activationRequested/switchId
```

手动和自动继续复用同一个内部函数：

```text
requestSceneSwitchLocked(roomId, target, switchId, source)
```

不要在持有房间锁时再次调用会重复取得同一把锁的 HTTP 路由，避免死锁。应提取出“已在锁内执行”的内部函数。

`GET /live/sync-candidates` 只负责读取和显示，不再承担推动自动状态机的职责。

也可以增加后端定时 evaluator，但 candidate heartbeat 内判断更简单，而且只有在线候选时才产生工作。

### 修复方案二：缓存 pending switchId 并持续接管

目标页面新增：

```text
pendingHandoffSwitchId
pendingHandoffDeadline
pendingHandoffTimer
```

收到 `activationRequested` 后：

1. 保存 switchId 和 deadline；
2. 立即调用带 switchId 的 claim；
3. 失败时每 500ms 重试；
4. 页面重新可见后使用缓存的 switchId 继续重试；
5. 必要时主动 GET 当前 handoff 状态恢复丢失的 switchId；
6. claim 成功、deadline 到期、目标改变或开关关闭时停止重试。

visibility handler 不能再调用无参 reclaim。应当：

```js
if (pendingHandoffSwitchId) {
    tryReclaimPublisher(pendingHandoffSwitchId);
}
```

同时调整 `tryReclaimPublisher()` 的门槛：

```js
// 普通无 switchId 的自主重抢仍然要求页面可见。
if (!switchId && !handoffVisible) return;

// 有服务端 switchId 时，不再由本地 visibility 否决。
// 最终安全性由后端校验 target instance、activation、deadline 和 generation。
```

后端 claim 继续严格验证：

```text
handoff.state === target-pending
switchId 完全一致
targetInstanceId === 当前页面 instanceId
targetActivationId === 当前页面 activationId
candidate publisherId 一致
deadline 未过期
```

因此移除本地 visibility 阻断不会允许其他隐藏页面随意抢占。

### 修复方案三：让自动执行与手动点击完全同构

“识别目标”和“执行切换”必须分成可观测的两个阶段：

```text
recommendedTarget：算法认为应该选择谁
switchRequested：已经成功创建服务端 handoff
```

UI 不能只因为存在 `targetInstanceId` 就显示“自动接管中”。只有以下检查全部通过才进入 switching：

```text
requestSceneSwitchLocked 返回 accepted=true
重新读取房间状态后 handoff.switchId 一致
handoff.state === target-pending
handoff.targetInstanceId/targetActivationId 与候选一致
```

自动请求的字段必须和手动按钮完全一致：

```json
{
  "targetInstanceId": "scene-b",
  "targetActivationId": "activation-b",
  "switchId": "auto-room-activation-b",
  "expectedGeneration": 11,
  "expectedInstanceId": "scene-a",
  "automatic": true
}
```

建议手动按钮和自动 evaluator 都调用同一个锁内函数，并返回相同结构：

```text
requestSceneSwitchLocked()
→ accepted
→ target-pending
→ target claim
→ completed
```

不能让自动模式只更新 `sharedAutoSwitchStates.targetInstanceId`，却没有持久化真正的 room handoff。

### 修复方案四：自动事务创建后立即唤醒目标

当 candidate heartbeat 本身触发自动切换，而且当前 heartbeat 就来自目标 activation 时，后端应在同一个响应中直接返回：

```json
{
  "activationRequested": true,
  "switchId": "auto-room-activation-b",
  "handoff": {
    "state": "target-pending",
    "targetInstanceId": "scene-b",
    "targetActivationId": "activation-b"
  }
}
```

不要等下一轮控制页 GET 或下一轮无关请求才把 switchId 传给目标。

如果创建自动事务的 heartbeat 来自其他候选，则目标下一次 heartbeat 必须取得同样的信息。

### 修复方案五：增加阶段日志

自动切换日志至少记录：

```text
AUTO_TARGET_SELECTED
AUTO_SWITCH_ACCEPTED
AUTO_TARGET_NOTIFIED
AUTO_CLAIM_ATTEMPT
AUTO_CLAIM_REJECTED + reason
AUTO_CLAIM_COMPLETED
AUTO_SWITCH_TIMEOUT
```

每条日志包含：

```text
roomId
switchId
targetInstanceId
targetActivationId
old/new generation
handoff state
```

这样可以区分“只完成算法选择”“已经创建 handoff”“目标没有 claim”和“claim 后播放失败”。

### 修复方案六：完整记录自动状态

自动状态增加：

```text
waiting
stabilizing
switching
completed
failed
ambiguous
disabled
```

目标 claim 成功时，根据 `switchId` 判断是否为自动切换，并写入：

```json
{
  "state": "completed",
  "switchId": "auto-...",
  "targetInstanceId": "scene-b",
  "generation": 12,
  "completedAt": 1786800000000
}
```

`completed` 至少保留 3～5 秒供控制页展示，再进入 `waiting/current-publisher-active`。

claim 超时或目标离线时写入 `failed`，不能一直停在 `switching`。

### 自动切换完整时序

```text
scene-a 被切走并停止 candidate heartbeat
→ scene-b 持续发送 candidate heartbeat
→ 后端发现 A 心跳年龄超过阈值
→ B 连续两轮成为唯一、无冲突目标
→ heartbeat 事务调用与手动按钮相同的 requestSceneSwitchLocked
→ 确认房间 handoff 已持久化为 target-pending
→ 同一个或下一次 B heartbeat 收到 activationRequested + switchId
→ B 不再被本地 visibility 阻断
→ B 缓存 switchId 并每 500ms 循环 claim
→ 后端 fencing A，授予 B 新 generation/leaseToken
→ B 恢复歌曲、进度和歌词
→ handoff/autoSwitch 均写 completed
```

### 验收测试

1. 不打开 control 页面，只运行 candidate heartbeat，也能完成自动切换；
2. heartbeat 第二轮达到稳定条件后创建一次且仅一次 switchId；
3. target heartbeat 响应包含 activationRequested 后，claim 成功并写 completed；
4. 第一次 claim 请求丢失，500ms retry 最终成功；
5. 页面隐藏再恢复后继续使用缓存 switchId；
6. switchId 丢失时能从权威 handoff 状态恢复；
7. 目标离线或 deadline 到期后停止 retry 并写 failed；
8. completed 在控制页至少显示 3 秒；
9. 自动和手动并发只允许一个房间切换事务；
10. 普通 OBS 页面不会触发 candidate evaluator。
11. `recommendedTarget` 存在但 requestSceneSwitch 失败时，UI 不能显示“自动接管中”；
12. 后端已经签发匹配 switchId 时，即使 `handoffVisible=false`，目标仍能 claim；
13. 错误 activation 或过期 switchId 即使页面 visible 也必须被后端拒绝；
14. 自动请求与手动请求生成的 handoff 数据结构完全一致；
15. 日志可以明确定位流程停在 selected、accepted、notified、claim 或 completed 哪一步。

## 问题三：下拉列表总显示 instance 冲突

### 根因

页面每次创建都会随机生成新的：

```text
publisherId
activationId
```

即使 URL 中的 `instance=scene-a` 固定，刷新或直播姬重新创建 WebView 后，activationId 仍会变化。

当前后端把同一 instance 下所有 TTL 内的 activation 都保留下来，并使用：

```text
freshActivationCount > 1
```

直接判定冲突。

页面刷新时会发生：

```text
旧页面 activation-old 最后一次心跳仍在 TTL 内
新页面 activation-new 开始心跳
→ 两条 activation 同时被判为 fresh
→ conflict=true
```

即使旧页面已经销毁，它还会在 8 秒 TTL 内造成假冲突。反复刷新会让冲突持续出现。

### 修复原则

“同一 instance 出现两个 activation 记录”不等于真实冲突。

只有确认两个不同页面在同一时间持续发送心跳，才算 instance 配置冲突。

### 第一层：刷新时复用 activationId

按房间和 instance 将逻辑页面身份保存到 `sessionStorage`：

```text
bilibili-order-song:handoff:<roomId>:<instanceId>:activation
```

页面普通 reload 时复用 activationId，不再每次随机生成。

真正的另一个标签页或另一个独立 WebView 通常有独立 sessionStorage，仍会生成不同 activationId。

不能只依赖这一层，因为直播姬销毁并重新创建 WebView 时可能同时清空 sessionStorage。

### 第二层：候选主动注销

新增或扩展：

```text
POST /live/sync-candidate-release
```

页面在 `pagehide`、明确 source-hidden 或 publisher release 时通过 sendBeacon 提交：

```json
{
  "room_id": "4646297",
  "instanceId": "scene-a",
  "activationId": "activation-old"
}
```

后端立即移除对应 activation。TTL 继续作为页面强杀时的兜底，不能只依赖 release 一定送达。

### 第三层：真实并发确认

服务端不要使用“fresh 数量大于 1”立即判冲突。每条 activation 增加：

```text
firstSeenAt
lastSeenAt
heartbeatCount
supersededAt
lastHeartbeatSequence
```

新 activation 第一次出现时：

- 将它标记为当前 provisional activation；
- 将旧 activation 标记为 superseded；
- 不立即设置 conflict；
- 进入约 4 秒确认窗口。

如果旧 activation 在被 superseded 之后没有再次心跳，说明它只是 reload 残留，应立即或在短 grace 后清理，不算冲突。

只有满足以下条件才判真实冲突：

```text
两个不同 activation
并且两者在彼此已被观察到之后都继续发送心跳
并且两者都至少连续发送 2 次心跳
并且心跳时间窗口存在重叠
```

这能区分：

```text
旧页面停止 + 新页面启动 = reload，不冲突
旧页面继续心跳 + 新页面也持续心跳 = 真实重复 instance
```

### 下拉列表状态

候选状态改为：

```text
online
reloading
conflict
offline
```

- `reloading` 可以手动选择，自动模式等待确认窗口结束；
- `conflict` 禁止自动选择；
- conflict 行显示两个 activation 的最近心跳，方便排查重复 URL；
- 不要因为 TTL 中的一条静默旧 activation 永久禁用整个 instance。

### targetActivationId

如果真实冲突仍存在：

- 手动切换必须携带明确的 `targetActivationId`；
- 后端只允许该 activation 对 switchId 执行 claim；
- 另一个同 instance 页面收到 handoff 也不能接管；
- 自动模式不得选择冲突 instance。

### 验收测试

1. 同一页面普通 reload 后 activationId 复用，不显示冲突；
2. sessionStorage 丢失产生新 activation，但旧 activation 不再心跳，不显示真实冲突；
3. candidate-release 成功后旧 activation 立即移除；
4. release 丢失时旧 activation 由 TTL 清理；
5. 两个独立页面使用同一 instance，并持续各发两次心跳，显示真实冲突；
6. reload grace 期间显示 reloading，不阻止手动恢复；
7. 冲突 instance 不参与自动选择；
8. 手动选择冲突 instance 时必须指定 targetActivationId；
9. scene-a、scene-b、scene-c 使用不同 instance 时互不冲突；
10. 反复切换/刷新 20 次后不会累积永久冲突记录。

## 修改位置

### `src/public/main.js`

- 设置响应增加 revision/sequence 保护；
- PUT 保存串行化，保存期间暂停或忽略旧 GET；
- 自动开关显示保存状态；
- 下拉列表区分 online/reloading/conflict；
- 自动 completed/failed 状态正确显示。

### `src/public/components/music-player.js`

- 不再无版本覆盖 `window.__displaySettings`；
- activationId 按 roomId + instanceId 写入 sessionStorage；
- 增加 candidate-release；
- 缓存 pending switchId 和 deadline；
- 有权威 switchId 时不再使用 handoffVisible 阻止 claim；
- 目标 claim 失败时按 500ms 重试；
- visibility 恢复时使用缓存 switchId；
- claim 完成或超时后清理 retry。

### `src/routers/bili-router.js`

- candidate POST 内触发自动 evaluator；
- 提取锁内 `requestSceneSwitchLocked()`；
